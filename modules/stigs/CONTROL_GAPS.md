# STIG control gaps and site-specific files

This document records findings from comparing the Puppet module with the SCC
RHEL 8 V2R7 and RHEL 9 V2R8 XML benchmarks. The module was generated from the
newer RHEL 8 V2R8 and RHEL 9 V2R9 Ansible roles, so each item must be confirmed
against the applicable current STIG before implementation.

The current manual XCCDF traceability audit is recorded in
`MANUAL_XCCDF_GAPS.md`. It compares all 1,248 rules in the RHEL 8 V2R8, RHEL 9
V2R9, and RHEL 10 V1R2 manual benchmarks dated 01 July 2026 with
`modules/stigs/files/` and `modules/stigs/manifests/`, including a detailed `V-`-keyed list of
settings and actions that are not represented in the module.
The companion `MANUAL_XCCDF_MODULE_COVERAGE.md` contains one Markdown-table
row for every `V-` identifier and names the Puppet manifest for each covered
row.

## RHEL 10 status

The official DISA RHEL 10 V1R2 manual XCCDF dated 01 July 2026 was reviewed
against the RHEL 10.2 reference VM. Release-specific and shared whole-file
assets now cover 68 safe static STIG destinations. The existing functional
manifests use RHEL 10 cases, guards, or release selectors for those assets. The
RHEL 8/9 package, service-state, and permission resources remain
release-guarded; full RHEL 10 STIG coverage and OpenSCAP results remain
outstanding. See
`STIG_CONTROLLED_FILES.md` for the file inventory and `SSG_COMPARISON.md` for
the earlier SSG comparison.

## Existing controls that need more information

### AIDE initialization and scheduling

The SSG profiles require AIDE installation and local database creation. Some
profiles also require periodic execution and notification, but the schedule,
notification recipient, exclusions, and database paths depend on the system
role. The module now installs AIDE on RHEL 8 and RHEL 9 but does not distribute
a database or a universal cron job. Initialize the database on each node after
reviewing a site-specific `aide.conf`, and manage the schedule and recipient as
parameters.

### Fapolicyd

The module installs and starts `fapolicyd` on RHEL 8 and RHEL 9, but
does not manage its configuration or policy. A deny-by-default policy is
organization-specific
and can prevent required programs from running if deployed without a tested
allowlist. Required decisions include:

- whether `permissive` mode is needed during policy development;
- which packages, binaries, interpreters, and application paths are trusted;
- whether the release uses the legacy `fapolicyd.rules` file or `rules.d`; and
- the deployment and rollback process for policy changes.

### System-wide cryptographic policy

The module installs `crypto-policies` but does not create or activate the STIG
subpolicy. Both SCC benchmarks specify this file:

```text
/etc/crypto-policies/policies/modules/STIG.pmod
```

with the following common content:

```text
# Define ciphers and MACs for OpenSSH and libssh
cipher@SSH=AES-256-GCM AES-256-CTR AES-128-GCM AES-128-CTR
mac@SSH=HMAC-SHA2-512 HMAC-SHA2-256
```

Activation requires `update-crypto-policies --set FIPS:STIG` and generally a
reboot. Confirm that FIPS mode is authorized and that any organization-specific
subpolicies are included before managing the active policy.

### PAM and authselect

The SCC benchmarks contain requirements for `password-auth`, `system-auth`,
smart-card authentication, faillock, password hashing, and pwquality. These
files are commonly generated by `authselect`; replacing them directly may be
overwritten later or may break authentication.

Before implementation, determine:

- whether each system uses `authselect`;
- the selected authselect profile and enabled features;
- whether a custom authselect profile is required;
- whether SSSD, local authentication, or smart cards are in use; and
- a tested recovery procedure for authentication failures.

## Files that must not be controlled wholesale

The following paths contain host-, environment-, or organization-specific
state. They should not be deployed as identical static files to every node.

| Path or area | Why a universal file is unsafe | Recommended Puppet treatment |
| --- | --- | --- |
| `/etc/fstab` | Depends on disks, UUIDs, mount points, and server role. | Use native `mount` resources or parameterized mount data. |
| `/etc/resolv.conf` | DNS servers and search domains vary by network and may be generated by NetworkManager. | Manage through NetworkManager or a parameterized resolver class. |
| `/etc/default/grub` | Contains existing kernel arguments and platform-specific boot configuration. | Manage required arguments with an idempotent `grubby` command or a parameterized complete configuration. |
| `/boot/grub2/user.cfg` and EFI equivalents | Contains password hashes and differs between BIOS and UEFI systems. | Supply secrets through an approved secret store and select paths using facts. |
| `/etc/grub.d/01_users` | Contains organization-selected GRUB users and password integration. | Use a protected template with externally supplied user and secret data. |
| `/etc/ssh/ssh_host*key` and public keys | Private host identity must be unique to each machine. | Manage permissions only; never distribute one common private key. |
| `/etc/ssh/shosts.equiv` | STIG requires absence rather than common content. | Declare the file `ensure => absent`. |
| `/etc/pki/rpm-gpg/` | Trust keys depend on approved repositories and release. | Manage approved individual key files or packages, not the entire directory. |
| `/etc/yum.repos.d/` | Repository URLs, credentials, and enabled repositories vary by environment. | Use parameterized repository resources or individually managed files. |
| `/etc/firewalld/zones/` | Allowed ports and services depend on system role. | Generate role-specific zones or use native firewall tooling with site data. |
| `/etc/rsyslog.d/` remote destinations | Log collector names, ports, certificates, and roles vary by site. | Use a parameterized fragment for forwarding; explicitly disable listener modules on non-collectors. |
| `/etc/sudoers.d/` | Privileged users and commands are organization-specific. | Manage individual validated fragments with mode `0440`; do not replace the directory wholesale. |
| `/etc/usbguard/rules.conf` | The allowlist depends on hardware attached to each system. | Generate per-node policy, distribute role-specific policy, or require an approved enrollment workflow. |
| `/etc/fapolicyd/rules.d/` | Executable allowlists depend on installed applications and server role. | Manage tested role-specific rules and retain an emergency rollback path. |
| `/etc/aide.conf` site paths | AIDE exclusions and monitored application paths vary by role. | Build from common audit-tool rules plus parameterized site rules. |
| `/etc/cron.daily/aide` notification target | Administrator email and schedule are site policy. | Use a template with configurable recipient and schedule. |
| `/etc/sssd/pki/sssd_auth_ca_db.pem` | Trust anchors depend on the organization's PKI. | Source from an approved certificate store; do not embed an unknown CA. |
| `/var/lib/aide/aide.db*` | AIDE databases are generated from each host's filesystem. | Initialize locally with guarded commands; never distribute a shared database. |
| `/var/log/*` and `/var/log/audit/*` | These are runtime records unique to each system. | Manage directory/file ownership and modes without controlling content. |
| `/var/log/faillock`, `/var/run/faillock`, and `lastlog` | These contain runtime authentication state. | Manage location, SELinux context, ownership, and mode only. |
| `/var/lib/tftpboot` | Content is service- and site-specific. | Remove/disable TFTP when unused; otherwise manage role-specific content separately. |

## Safe resource-level controls

Several SCC requirements reference dynamic files but only require metadata or
absence. These can be implemented without controlling content:

- permissions and ownership for SSH host keys, audit logs, and account files;
- absence of `shosts.equiv` and other prohibited trust files;
- ownership and mode of audit configuration directories;
- service enablement, disablement, and masking;
- package installation or removal; and
- mount options through native `mount` resources.

Any future implementation should preserve the module's existing RHEL fact
selection: common resources should be declared once, and genuine RHEL 8/9
differences should remain inside the same functional manifest.
